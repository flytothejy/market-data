# AI 조건 검색 — 문장으로 종목 걸러 찾기

> 2026-10-28 설계. 상태: 문서·필드 사전 완료 / Worker·화면 미구현.
> 필드 사전: `hub/spec/screen_catalog.json` (`python -m hub.screen_catalog <universe.json>`으로 생성)
> 평가 문장: `features/ai-screen/eval.json`

## 1. 무엇을 하나

사용자가 문장으로 조건을 말하면, AI가 그 문장을 **기존 조건 검색 필터로 번역**한다. 종목을 거르는 일은 지금 검색 화면과 똑같이 브라우저가 `universe.json`에서 한다.

> "최근 실적 서프라이즈가 4분기 연속이고, 매출·순이익이 늘고, 한 달 안에 골든크로스가 난 종목"
> → `최근 4분기 상회 횟수 ≥ 4` · `매출 성장 > 0` · `순이익 성장 > 0` · `골든크로스 30일 안`
> → (지원 안 됨) "매출·순이익이 *연속 분기로* 늘었는지는 아직 조건이 없어요. 1년 성장으로 대신했어요."

**하지 않는 것**: 종목 추천, 오를 종목 예측, 종목 이름을 AI가 직접 고르기, 특정 투자자 이름 같은 사전에 없는 조건 지어내기.

## 2. 원칙

1. **AI는 번역만**: AI가 받는 것은 문장과 필드 사전뿐이다. 종목 목록·가격은 주지 않는다. 그래서 결과에 AI가 지어낸 종목이 섞일 수 없다.
2. **보이는 조건**: 번역 결과를 칩으로 먼저 보여 준다("이렇게 이해했어요"). 사용자가 칩을 고치거나 지울 수 있고, 결과는 칩 기준으로만 나온다.
3. **없는 조건은 솔직하게**: 사전에 없는 조건은 비슷한 조건으로 몰래 바꾸지 않는다. `unsupported`에 적어 화면에 표시한다. 대신 쓸 수 있는 조건이 있으면 `assumptions`에 "이걸로 대신했어요"라고 적는다.
4. **모호한 말은 기본값 + 고지**: "대형주", "고배당" 같은 말은 사전의 `vague` 기본값을 쓰고, 어떻게 봤는지 `assumptions`에 적는다.
5. **추천·예측 요청은 번역하지 않음**: "오를 종목", "살 만한 종목" 같은 요청에는 조건을 만들지 않고, 조건으로 다시 말해 달라고 안내한다(예시 조건 2~3개 제시).
6. **사이트 표현 원칙 유지**: 칩·안내 문구에 추천·예측·'검증' 표현을 쓰지 않는다.

## 3. 흐름

```
[검색 화면 입력창] ──문장──▶ [Worker /ai/screen]
                                 │  필드 사전(screen_catalog.json) + 규칙(시스템 프롬프트)
                                 ▼
                           [Claude API, 작은 모델] ──JSON──▶ [Worker 검증]
                                                                 │ key가 사전에 있나, 형태·숫자 맞나
                                                                 ▼
[검색 화면] ◀── 조건 JSON ─────────────────────────────────────────┘
   칩으로 표시 → 사용자가 고침 → 브라우저가 universe.json에서 거름
```

- 결과 화면 주소에 조건을 담아(`screen.html?q=<조건 JSON>`) 공유·북마크할 수 있게 한다. 같은 주소를 열면 AI를 다시 부르지 않는다.

## 4. 출력 형식 (AI → Worker → 화면)

```json
{
  "kind": "stock",
  "conds": [
    {"k": "c_beats", "min": 4},
    {"k": "rev_g", "min": 0},
    {"k": "ni_g", "min": 0},
    {"k": "gc", "past_days": 30},
    {"k": "sec", "in": ["Technology"]},
    {"k": "dz", "in": [0]},
    {"k": "dvc_v", "is": 0}
  ],
  "query": null,
  "sort": {"k": "mcap", "dir": "desc"},
  "assumptions": ["'매출·순이익 증가'는 최근 4개 분기 합의 1년 성장으로 봤어요"],
  "unsupported": ["매출·순이익의 연속 분기 증가 여부"],
  "refused": null
}
```

| 필드 | 뜻 |
|---|---|
| `kind` | `stock` \| `etf` |
| `conds[]` | 조건 목록 (모두 AND). 형태는 아래 표 |
| `query` | 이름·티커 검색어 (예: "엔비디아 같은 반도체 회사"는 query가 아니라 업종 조건) |
| `sort` | 정렬 기준 (없으면 시가총액 큰 순) |
| `assumptions[]` | 모호한 말을 어떻게 해석했는지, 무엇으로 대신했는지 (사용자에게 보임) |
| `unsupported[]` | 사전에 없어 반영하지 못한 조건 (사용자에게 보임) |
| `refused` | 추천·예측 요청일 때 안내 문구, 그 외 null |

조건 형태 (필드 사전의 `type`)

| type | 형태 | 예 |
|---|---|---|
| `range` | `{"k","min"?,"max"?}` — pct는 0.1 = 10%, usd는 달러 | `{"k":"dy","min":0.04}` |
| `date` | `{"k","past_days"}` 또는 `{"k","next_days"}` | `{"k":"gc","past_days":30}` |
| `enum` | `{"k","in":[...]}` — 사전의 values 중에서 | `{"k":"idx","in":["S&P500"]}` |
| `flag` | `{"k","is":0\|1}` | `{"k":"dvc_v","is":0}` |

OR 조건, 두 필드 비교(예: 최근 분기 성장 > 1년 성장), 순위(상위 N개)는 1단계에서 지원하지 않는다 → `unsupported`.

## 5. Worker 검증 (AI 출력을 그대로 믿지 않음)

- JSON이 아니면 1회 재시도, 그래도 아니면 "이해하지 못했어요" 안내
- `k`가 사전에 없으면 그 조건을 버리고 `unsupported`로 옮김
- `type`과 형태가 다르면 버림 (예: date 필드에 min)
- 숫자는 유한값만, pct 필드에 1보다 큰 값이 오면(예: 20을 20%로 착각) 100으로 나눠 보고 assumptions에 적음
- enum 값이 사전 values에 없으면 버림
- 조건 0개 + refused 없음 → "조건을 찾지 못했어요" + 예시 문장

## 6. 시스템 프롬프트 골자

- 너는 문장을 조건 JSON으로 바꾸는 번역기다. 종목을 고르거나 평가하지 않는다.
- 아래 필드 사전의 key만 쓴다. 각 필드의 `desc`·`say`·`note`를 따른다.
- 값의 크기는 `p10`/`p50`/`p90`을 참고해 현실적인 범위로 정한다(예: "높은 ROE"는 p90 근처).
- 모호한 말은 `vague` 기본값을 쓰고 `assumptions`에 적는다.
- 사전에 없는 조건은 지어내지 말고 `unsupported`에 사용자의 말 그대로 적는다.
- 추천·예측 요청(`refuse` 목록과 비슷한 뜻)은 `refused`에 안내를 쓰고 conds는 비운다.
- JSON 하나만 출력한다.

필드 사전(약 22KB)은 매 요청 같으므로 프롬프트 캐시를 쓴다.

## 7. 화면

- 검색 화면 맨 위에 입력창: "문장으로 찾기" — 예시 문장 3개를 버튼으로 (누르면 바로 실행)
- 결과 위에 "이렇게 이해했어요" 줄: 조건 칩(기존 칩과 같은 모양, 고치기·지우기 가능)
- 그 아래 작은 글씨: assumptions(회색), unsupported("아직 지원하지 않는 조건: …", 주황)
- 날짜 조건 칩: "골든크로스 30일 안", "실적 발표 7일 안"
- 지금 검색 화면은 숫자 범위만 받으므로 `date`·`enum`·`flag` 조건 처리를 추가해야 함 (필터 함수 확장)

## 8. 운영

| 항목 | 정책 |
|---|---|
| 모델 | Claude 작은 모델(빠르고 쌈). 평가 정확도가 낮으면 한 단계 위 모델 |
| 비용 | 요청당 입력 약 8천 토큰(캐시) + 출력 수백 토큰 — 1원 안팎 예상 |
| 키 | Claude API 키를 Worker 비밀값으로 (사용자가 직접 등록, 저장소에 넣지 않음) |
| 제한 | 로그인 사용자 하루 20회, 비로그인은 예시 문장만. Worker에서 사용자별 카운트(D1) |
| 기록 | 문장·결과 조건·unsupported를 D1에 저장(개인 식별 없이) → 자주 나오는 unsupported로 필드 추가 우선순위 결정 |
| 유료화 | 횟수 확대를 유료 후보로 (pitch §7) |

## 9. 평가

`eval.json`의 문장마다 기대 조건을 적어 두고, 프롬프트·모델을 바꿀 때마다 돌린다.

- 통과 기준: key 집합 일치 + 숫자는 기대 범위 안 + unsupported/refused 판정 일치
- 목표: 25문장 중 23개 이상 통과(92%)
- 실패 문장은 사전의 `say`·`note`를 고쳐서 해결 (프롬프트를 길게 늘리기보다 사전을 고침)
